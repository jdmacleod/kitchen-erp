## Problem Statement

Receipt reading misses the printed total too often to trust. In the most recent dogfood run (issue #121), 9 of 12 real receipts failed to reconcile.
- Tesseract (`--psm 6`, 200 dpi) drops prices and decimal points.
- The text model (`gpt-oss:20b`) reads the OCR text in 25-row parts and takes 30–140 s for the lines stage.
- It never fills `qty` for plain item lines.

Review then means re-keying numbers, which defeats the point of ingest.

A vision-capable model reads the photo directly, the way a person does. The household's LAN Ollama host already serves several: `qwen3-vl:30b`, `qwen3-vl:8b`, `minicpm-v4.5:8b`, `glm-ocr`, `granite3.3-vision:2b`, `llama3.2-vision:11b`, `mistral-small3.2`, and the Gemma 3 and 4 families. The 2026-10-01 survey adds `qwen3.5:9b`, `qwen3.6:27b` and `qwen3.8:27b`, already on the host, and finds two of the original list unusable (see "Model survey").

The goal (D3) is **totals reconcile, and review becomes a glance and a confirm.**

## What Makes This Cool

A receipt carries three kinds of evidence about its own reading:
1. the printed total;
2. each row's own arithmetic (weight × rate = amount, count × unit = amount);
3. a second, independent reading.

Four open-source receipt projects were read for this session (source read on GitHub, 2026-09-30). **None uses a second reader** (corrects R2-3):
- **Rudd-O/beanhand** is a vision model that writes ledger text, with no arithmetic check.
- **Endle/beanbeaver-core** is OCR plus rules, with per-row arithmetic and total checks.
- **natelandau/cartlog** is a vision model with a line-sum check against the total, and has no tax field.
- **vpopovec/Grocery-Tracker** has a vision model asked to "verify its math". The code never checks it.

Here a vision model reads the photo, and everything else is evidence about that reading:
- code does all the math;
- a second vision model from another family reads it too;
- OCR text acts as a soft, decimal-tolerant witness;
- where the readers disagree, the printed total picks the combination that adds up.

**What is and isn't independent (R2-1).** The total is printed on the image, so the vision reader sees it, and a reading can fit its lines to its own misread total. The prompt therefore never states a total and never asks the model to check its math. Independence comes from three things: the per-row arithmetic, the second reader, and the OCR witness (including `total_witness_mismatch`). The benchmark scores against the total a person committed, never the model's own (Phase 0).

## Premises (agreed in D6; P3 revised in D8)

1. **Local only.** Vision calls go through `OLLAMA_BASE_URL`. No cloud provider is built, and images never leave the household network.
2. **Code does the math.** Models fill the existing Decimal-string schemas (`ReceiptHeader`, `ReceiptLines`). `refine_line`, `merge_quantity_lines`, `fold_regular_prices`, `check_prices` and `reconcile` run unchanged on every reading. No prompt asks a model to check its own math.
3. **OCR is a soft witness.** Missing OCR support raises a review flag; it never blocks, drops or gates anything.
4. **The auto-accept bar is unchanged.**
   - `stage_resolve` always sets `needs_review`, and a person commits.
   - Products resolve without a person only by barcode or a confirmed alias.
   - A combination "matched the total" is a preselection a person confirms, never an auto-commit.
5. **Evidence first.** The benchmark runs locally on the household's receipts and prints aggregate scores only. Per-receipt output stays under `data/`. Committed fixtures are synthetic images.
6. **Slow is fine, within a bound.** Each receipt has one vision time budget (VD8).

## Approaches

All outcomes start with the same benchmark (Phase 0).
- **A, vision as OCR adapter (effort S).** The `vision` `OcrAdapter` described in `ocr.py:8-12`: a vision model transcribes the image, and the text pipeline is unchanged.
- **B, vision reader with OCR witness (effort M), chosen in D9.** A vision reader fills `ReceiptHeader` and `ReceiptLines` from the image, and every deterministic post-pass runs unchanged.
- **C, consensus (effort L), accepted into Phase 1 as VX4 and gated by Phase 0 (VD1).** B plus a second vision model from another family. OCR amounts supply per-line candidates, and the printed total picks among them.

## Phase 0: `kerp reading-benchmark` (VX1, VX2, VD11)

A lasting `kerp` subcommand in `backend/app/cli.py`, with its logic in `backend/app/services/reading_benchmark.py`.

**Runbook (EV5).** Stop the worker first, so no upload or naming pass swaps models during the run, then run detached:

```
docker compose stop worker
docker compose run -d --name kerp-bench api kerp reading-benchmark [--models m1,m2] [--resume RUN_ID]
docker compose logs -f kerp-bench    # or follow /data/benchmarks/reading-runs/<RUN_ID>/log.txt
docker compose start worker          # afterwards
```

- The command warns, and asks for `--force`, if the worker is running.
- Screening runs one configuration over every receipt before the next, so swaps don't dominate. Only arm (d) interleaves models per receipt, as production would.

**It writes nothing to the app database (R2-7).**
- It calls the readers, the OCR adapters, header parsing and the pure post-passes (`refine_line`, `merge_quantity_lines`, `fold_regular_prices`, `check_prices`, `reconcile`) directly. It never calls `stage_*`, `run_stage` or `upsert_draft_purchase` (N2-3).
- Its database access is SELECT only: committed purchases, their lines and aliases. It runs inside a transaction that is always rolled back.
- A test asserts that the row counts of `ingest_stage_result`, `purchase`, `purchase_line`, `price_observation` and `receipt_alias` are unchanged after a run on fixtures.

**Paths (R2-8).** Inside the container `./data` is mounted at `/data` (compose.yaml:61), so everything lives under `/data/benchmarks/`:
- `reading-runs/<RUN_ID>/readings.jsonl`: per-reading checkpoint, used to resume.
- `reading-runs/<RUN_ID>/summary.txt`: the aggregate table.
- `reading.csv`: one aggregate row per configuration per run. The columns are `run_id, started_at, receipt_set_hash, arm, model, second_model, model_digest, prompt_version, long_side, variant, n, reconcile_share, consensus_share, runaway_share, header_total_exact, item_count_mad, alias_hit_rate, ocr_support, ocr_support_tolerant, false_support, vlm_agreement, box_valid_share, box_iou50_share, seconds_p50, seconds_max, tokens_p50, load_seconds_p50, model_tag, line_amount_exact_share, wrong_preselection_count, ci80_low, ci80_high`.
  - "Previous best" means the highest `reconcile_share_mean` among rows with the same `receipt_set_hash` (sha256 of the sorted document ids). The receipt set is fixed when the run starts.
- `expected.csv` (optional).

Per-receipt files stay under `data/` and are never read by the assistant.

**Extraction first (N3-2).** Today's text reading (`_read_lines_in_parts` and its parts and re-ask logic) and the header total rule (`printed_total_line` plus the `total_from_text` override) move out of `stage_lines` and `stage_header` into pure functions in `ingest/readers.py`. The stages call them, and a test asserts that stage output is unchanged for every receipt fixture. Arm (a) calls the same functions, so it is today's pipeline exactly.

**Which receipts, and what counts as the truth (VX1, C1-5, C3-2).**
- **Receipts scored:** purchases with `status = 'committed'` and a `receipt_document_id`. Voided purchases are excluded.
- **Expected total:** `purchase.total`. These purchases are excluded:
  - those flagged `total_missing`, because their total was computed rather than printed;
  - (OV5) those still flagged `reconcile_mismatch`;
  - (OV5) those whose total came from `total_from_text` with no edit by a person, because the old pipeline's misread could otherwise be scored as the truth.

  The number excluded for each reason is printed.
- **Expected item count:** the committed purchase's lines with `line_kind = 'item'` that aren't removed. This counts after the post-passes and any human edits, and the arms are compared on their own post-pass item count.
- **Optional `expected.csv`:** for receipts never committed. Columns are `document_id,total,item_line_count`, and a synthetic example drives the command's unit test.
- **Sample size (R2-13):** n is the number of eligible receipts, printed with every result. The #121 baseline is 12; today's household store has about 14 uploaded, and only committed ones count.
- **Qty fill rate:** measured only by the live synthetic suite (Success Criteria), not on real receipts.

**Arms.**
- (a) today's pipeline;
- (b) vision-as-OCR: a vision model transcribes, then the current text lines stage runs;
- (c) vision reader (B);
- (d) vision reader plus consensus (B+C), using a second model from another family (VD1, VD2).

**Two steps (OV3).**
- **Step 1** builds and runs arms (a), (b) and (c) only.
- **Step 2:** the consensus engine (alignment, candidates, search) and arm (d) are built and run only if (c) ships under the rule below and still leaves more than 1 in 5 eligible receipts unreconciled.
- Otherwise consensus goes to TODOS.md with the step 1 table.

Arm (c) runs in two variants: one call for header and lines, and separate calls.

**Grid (OV4, reduced).**
- Candidates: ~~one per family, the instruct tags of `qwen3-vl:8b` and `minicpm-v4.5:8b` (OV9)~~ superseded by MS4: `qwen3.5:9b`, `gemma4:12b`, `minicpm-v4.5:8b` and `qwen3.6:27b`, plus `gemma4:26b-a4b` if pulled. Instruct or `think: false` only (OV9). `glm-ocr` runs in arm (b) only.
- Long-side cap: 2000 px only.
- Arm (c) runs only the separate-calls variant. The one-call variant is dropped unless a later run shows it is much faster.
- Whole images only; slicing is deferred (VH1, which also removes R2-11).
- Arm (d), in step 2 only, pairs the best (c) model with the best (c) model from another family (MS5).

**Staged runs (VD11, R2-6).**
- **Order:** arms (a), (b) and (c) first; arm (d) after the best (c) configuration is known.
- **Screening:** every configuration runs once.
- **One run per configuration (EV6, superseding the ×3 confirmations from VD11 and N3-4).** Every call is at temperature 0, so repeats would return almost the same answer. The time goes to receipts instead: before Phase 0 the household is encouraged to commit more receipts or add `expected.csv` rows. The 80% intervals (OV4) and the hold-out batch remain the checks on chance.
- Results are checkpointed per reading, so `--resume` continues a stopped run.
- `--models` adds just a new model against the stored best.
- Estimated time is printed before starting: configurations × n × p50 seconds, with arm (d) counted at twice the per-receipt time plus about 4 s of swaps.

**Scores (aggregates only).**
- **Reconcile share (R2-2):** first-reading lines, discounts, tax and fees summing to the **expected** total within 0.02. One run per configuration (EV6).
- **Arm (d)'s headline (N2-4)** is the share whose preselected consensus combination, or its first reading when nothing is preselected, sums to the expected total within 0.02. Re-ask results are excluded. Arm (d) also reports:
  - the share reconciled by consensus;
- **Line accuracy (OV2):**
  - `line_amount_exact_share`: aligned item lines whose amount equals the committed line's amount;
  - for arm (d), `wrong_preselection_count`: receipts whose preselected combination differs from the committed amounts.
- **Intervals (OV4):** each share is printed with a binomial 80% interval.
- Exact header-total match against the expected total.
- Mean absolute item-count difference.
- Seconds per receipt (p50, max) and tokens per receipt, from the call ledger (VX7).
- **Alias hit rate (R2-5, F5-6):** the share of item lines whose `raw_text_norm` hits a confirmed vendor alias. Each receipt is scored only against aliases whose `created_at` is earlier than the receipt's `purchase.created_at`, meaning they existed before the receipt was drafted (N2-7). There is a limitation: an alias rewritten in place keeps its original `created_at`. This is stated in the output.
- **Witness quality**, on lines whose amount equals the committed line's amount:
  - Tesseract support rate, with and without decimal tolerance;
  - two-model agreement rate;
  - **false-support rate:** perturbed amounts (±0.01 and ×10) that still find support.
- **Box quality per model (VD7):** on real receipts, the share of lines that come back with a valid box. On synthetic fixtures, where the renderer knows where each line was drawn, the share of boxes that overlap the true line by at least 50% (intersection over union of 0.5 or more).
- Run time is printed and estimated before starting. As an example, from the measured speed (E2: about 36 tok/s, about 150 s per reading; EV9): step 1 is about 6 configurations × 12 receipts × 150 s, roughly 3 hours. Step 2, if it runs, adds about 1 hour for arm (d).

**Decision rule (R2-4, VD1, VD9, VD10).** Steps 1 and 2 apply within an arm; the rest compares arms.
1. **Pick each arm's configuration.** It is the one with the highest mean reconcile share. Ties go to the higher alias hit rate, then fewer seconds.
2. **Margin (OV4).** A difference counts only if it exceeds the larger of 3 receipts and 1/n. Anything inside the margin is "no decision" between the two.
3. **Bars (OV1).** Drop any of (b) and (c) that fails any of these:
   - a reconcile share of at least 75%;
   - beating arm (a) by more than the margin;
   - an alias hit rate no more than 5 points below (a)'s.
4. **Pick the reader.**
   - Neither (b) nor (c) is left: **ship neither**. The benchmark stays for the next model.
   - Only one is left: **ship it.**
   - Both are left: ship (c) unless (b) beats it by more than the margin. Within the margin, prefer B (VD10).
5. **Consensus (VD1, OV2, OV3).**
   - Arm (d) runs only under OV3's step 2.
   - Consensus ships only if all of these hold:
     - (d) beats (c) by more than the margin;
     - its `line_amount_exact_share` is no lower than (c)'s;
     - its `wrong_preselection_count` is at most 1.
   - Otherwise consensus goes to TODOS.md with the table. Crops then use their own trigger (D14).
6. **If A or neither ships,** consensus (VX4) and crops (VX5) go to TODOS.md with the Phase 0 table (VD9). The re-ask is already deferred (OV6a).

**Hold-out (R1-15).** Success is declared only after the chosen configuration holds within one receipt of its share on the next dogfood batch of at least 10 receipts that took no part in tuning.

`backend/scripts/ocr_benchmark.py` stays as it is; the new command replaces it for vision work.

## Model survey (2026-10-01, MS1–MS6)

The user asked for a survey of the Ollama vision catalogue as of October 2026, for a 24 GB Apple M4 Pro laptop, because newer models such as `qwen3.6:27b` were missing from the grid. This section records the survey and a probe of every vision model already on the LAN host. Where it changes an earlier value, the "Start here" table lists the change.

**Hardware correction (MS1).** On the LAN host (Ollama 0.34.4), one model can hold up to about 16.2 GB in GPU memory. That is consistent with macOS's default GPU limit on a 24 GB Apple silicon machine, about two-thirds of RAM. The earlier "10.6–12.8 GB usable" came from which *pairs* of models stayed resident, not from a single model's ceiling. A model larger than about 16 GB at 16k context still loads, but its excess layers run on the CPU and generation slows to 8–13 tok/s. Raising the limit (`sudo sysctl iogpu.wired_limit_mb=20480`, reset at reboot) should let a 27B model fit entirely, at the cost of memory for everything else. Nothing in the plan assumes it; only the household can decide to do that, and it is not tested.

**Probe (MS2).** Method:
- Three synthetic fixtures (`supermarket_loyalty`, `discount_grocer_terse`, `warehouse_codes`) were rendered with the test helper.
- Each model got one call per fixture: JSON-schema `format`, temperature 0, 16k context, 8192 output cap, `think: false` where the model supports thinking.
- The score is the printed line amounts recovered (24 in total across the three fixtures), the amounts invented (extra), and whether the total was read correctly.

These are clean renders of short receipts, so accuracy here only screens out broken models. It does not rank the good ones; Phase 0 on real photos does that. Fit, speed, image tokens and thinking behaviour do carry over.

Two findings change how the benchmark runs:
- **Thinking (confirms OV9).** The default `qwen3-vl` tags are the thinking variants and ignore `think: false`. `qwen3-vl:8b` spent its whole 4,096-token budget thinking on 2 of 3 receipts. - **Output size.** A transcribed line costs about 30–35 output tokens without boxes. A 60-line receipt is therefore about 2,000 tokens; the 4,000–5,000 estimate with boxes (E2) is still unverified. At 12.6 tok/s, `qwen3.6:27b` takes about 160 s for 60 lines without boxes, but about 400 s at 5,000 tokens. That is over the 300 s call timeout, so with boxes a 27B model only fits the budget if the GPU limit is raised.

## Phase 1-B: vision reader, consensus and crops (if B wins)

### Reader seam

- `ReceiptReader` has `name` and `version`, plus:
  - `async read_header(ctx) -> ReceiptHeader`
  - `async read_lines(ctx) -> ReceiptLines`
- The header and lines stages call them, so each stage keeps its own `ingest_stage_result` and retry.
- If Phase 0 picks the one-call variant, `read_header` stores the validated lines payload in its stage output, and `read_lines` reuses it on the first pass. A lines-stage retry or fallback never reuses it (R2-10).
- `READ_ADAPTERS` defaults to `["text"]`, which is exactly today's behaviour; `["vision", "text"]` turns vision on.

### Fallback (mirrors `OcrUnavailable`; F5-1, R2-10)

- **`llm.py` change (N2-8).** `chat()` raises `ModelMissing`, a subclass of `ModelUnavailable`, only for a 404 whose body is Ollama's "model … not found".
  - Callers that catch `ModelUnavailable` keep waiting, exactly as today. That includes the text path and naming.
  - Only the vision reader converts `ModelMissing` into `ReaderUnavailable`.
  - A proxy's bare 404 stays `ModelUnavailable`.
  - **A text-only model (eng E1, D3).** A 400 whose body says the model doesn't support multimodal input is also `ModelMissing`. The vision reader falls back to text, the purchase gets `vision_model_not_multimodal`, and the worker logs a warning naming `VISION_MODEL`. This was confirmed against Ollama 0.34.4 with a synthetic image.
- **`ReaderUnavailable`** tries the next reader at once. It is raised for:
  - `ModelMissing` for the vision model;
  - a document that can't be rasterised;
  - a spent budget (VD8) before the primary reading is valid;
  - a timeout, `model_out_of_room`, or invalid replies after the retries.
- **Fallback is per stage.**
  - The stage that fell back records `read_fallback` in its output and on the purchase.
  - Lines that fell back use the text reader's OCR-derived `raw_text` for alias lookup.
  - A purchase can therefore have a vision header and text-path lines; review shows `read_fallback`.
- **An empty reading is invalid (GAP-2).** A vision reply that validates but has 0 item lines counts as invalid, toward retries and then fallback. This applies to a page with 3 or more amount-like OCR tokens, or to any image when there is no OCR text. It is today's empty-part rule from #60, applied to vision.
- **A valid primary reading that doesn't reconcile never falls back.** It goes on to consensus, if consensus shipped, and otherwise to review with its flags.

### Budget (VD8, R2-9, F5-3)

- `VISION_JOB_BUDGET_SECONDS` defaults to 900 per receipt.
- **What counts (N2-2).** The budget is the sum of `calls[].seconds` with a vision role, across **all** of this job's stage results, not only the latest per stage. Failed attempts count too, because the failure-path output also carries `calls` (see Call ledger). Job retries don't reset it, and no migration is needed.
- **Per-stage cap (D12, N2-1).** Each vision stage stops at the existing `lines_deadline_seconds()` (0.8 × `INGEST_LOCK_TIMEOUT_SECONDS`, 480 s by default). Each call's timeout is the smaller of `VISION_TIMEOUT_SECONDS` and the stage time left, so a stage never outlives the job lock and a receipt is never read twice.
- When the budget is spent:
  - the optional call (the second model) is skipped with a `vision_budget_spent` flag;
  - later PDF pages are part of the primary reading, not optional (N3-7). If the budget runs out before they are read, the primary reading is incomplete, so the reader falls back;
  - if the primary reading isn't complete yet, the reader raises `ReaderUnavailable`.
- **One stage clock (D16, N3-1).** A stage's deadline starts once, when the stage starts. The vision reader and any text fallback draw from the time left. If less than 120 s is left when vision gives up, the stage ends with a retryable failure that records `read_fallback`, and the next attempt starts directly with the text reader. The text reader's parts deadline takes the stage's remaining time instead of starting its own. A test with a fake slow model asserts that no stage runs past 0.8 × lock.
- **Worst case per receipt:** vision header up to 480 s, plus vision lines up to 420 s (the 900 s budget is then spent), plus the text fallback's lines stage up to 480 s. That is about 23 minutes, and no stage exceeds the lock.
- **Typical case (EV9, measured speeds):** about 2.5–3 minutes per receipt for a single reading, about 5–9 minutes with consensus, plus about 8 s of ranker swaps.
- **A batch of 10:** about 30–50 minutes without consensus, about 60–90 with it; worst case about 4 hours.
- Review of finished receipts stays usable throughout, because the API doesn't wait on the worker. Worker concurrency stays out of scope.

### Image prep

- Apply the EXIF orientation and cap the long side at `VISION_MAX_LONG_SIDE` (default 2000 until Phase 0 picks; R2-14).
- **Colour (EV10).** `raster.py` gains a colour-preserving render for vision prep and the review image. Tesseract keeps today's grayscale converters (raster.py:65, :80). PDFs render at the existing 200 dpi. Phase 0 scores exactly this prep.
- **Page 1 only (EV7).** `VISION_MAX_PAGES` is 1: a till receipt doesn't run to two pages (raster.py:49), and more pages can't fit the stage clock. A PDF with more pages gets `pages_truncated`, which review shows. SC-1's multi-page renderer is dropped.
- HEIC goes through the existing raster conversion, and every render keeps `raster.py`'s 80 MP cap.
- **One orientation step (N2-13).** Vision prep and the review image render (`receipt_images`) share one orientation function, so a HEIC or PDF rendered to PNG is upright in both places, and the boxes line up. A rotated synthetic HEIC fixture tests that a box drawn on the vision image lands on the same text in the rendered image.
- The stored original and its sha256 identity don't change. The image endpoint's contract doesn't change, but every render it serves, including scaled JPEG thumbnails (`?width=`), goes through the shared orientation step and comes out upright. Today a scaled rotated JPEG is sideways, a small existing bug this fixes (N3-8). Crops use that output.

### `llm.py`

- Image parts go into the `/api/chat` message with the same JSON-schema `format`, validation and `model_out_of_room` handling.
- Each call has a per-call `VISION_TIMEOUT_SECONDS`.
- **Vision retries (EV1).** A vision call makes one attempt, then one retry at temperature 0.3 (`EMPTY_PART_RETRY_TEMPERATURE`, the #60 rule), then falls back. The text path keeps `1 + LLM_MAX_RETRIES` tries. `extract()` takes the retry policy as an argument, since it is shared.
- **Thinking off (OV9).** Settings name exact instruct tags, never thinking variants. Vision calls pass `think: false` where the model supports it, and `reading.csv` records the tag. This guards against #60's failure, where reasoning filled the context and the answer came back empty.
- **Load time (OV7).** `last_usage` also carries `load_seconds`, from Ollama's `load_duration`. The budget counts it, because swaps are real time. The benchmark reports it separately, and arm (d) runs interleaved (primary, then second model) per receipt, as production would.
- **Measured (eng E2, 2026-10-01; ceiling corrected by MS1).** The host keeps only one vision model resident at a time. One model can use up to about 16.2 GB of GPU memory; the 10.6–12.8 GB figure was the limit for a pair. qwen3-vl:8b is 6.55 GB at 16k and minicpm-v4.5:8b is 10.29 GB at 16k, so together they don't fit, and gpt-oss:20b (12.83 GB) evicts both.
  - Consensus therefore pays a model swap on every receipt (2–4 s measured), and a text fallback pays another.
  - Generation runs at about 36 tok/s, so a 60-line answer with boxes (about 5,000 tokens) takes about 2–3 minutes per reading.
  - The README states the 16k context and this single-resident behaviour, and Phase 0 prints the measured swap cost.
- **Context (D4) and output cap (EV2).** Vision calls use `VISION_NUM_CTX = 16384` and `VISION_NUM_PREDICT = 8192`, constants beside the text path's 8192. 8,192 tokens at about 36 tok/s is about 230 s, inside the 300 s call timeout, so a runaway reply shows up as `model_out_of_room` rather than a timeout. Phase 0 reports timeouts and out-of-room together as a "runaway" rate. The 16k context was verified to fit fully in GPU memory and to complete a 13k-token generation.
- **Usage (F5-2).** `chat()` exposes usage the way it already exposes `last_done_reason`: `last_usage = {prompt_tokens, completion_tokens, seconds}`, taken from `prompt_eval_count`, `eval_count` and `total_duration` (which is in nanoseconds, converted to seconds).

### Call ledger (VX7, C1-6)

- Each stage output gains `calls`, a list with one entry per model call attempt, including retries, fallbacks and the second model:
  `{"role": "primary|second|text", "model", "model_tag", "prompt_version", "seconds", "load_seconds", "prompt_tokens", "completion_tokens", "outcome": "ok|invalid|timeout|out_of_room|missing|unavailable"}`
- **Where it is held (N2-2).** The ledger is kept on the `LlmClient`, and each attempt is appended as it ends. `run_stage` writes it into the stage output on success, and also into the failure-path output (`{"ok": false, "error", "retryable", "calls"}`), so timeouts and unavailable calls are recorded.
- The list lives in the existing JSONB `output`, so no migration is needed.
- Logs carry ids and counts, never receipt or model text.

### Untrusted image content (R2-17)

- Text printed on a receipt reaches the model inside the image and can't be delimited as data. The system prompt still says to extract only.
- Schema validation followed by the deterministic post-passes is the only acceptance path.
- The default suite feeds a recorded adversarial reply for a synthetic injection image. It asserts that the reply is rejected by schema validation or handled inertly: no field outside the schema, and no instruction text acted on.
- The live `-m llm` arm includes the injection image as an observational check.

### Prompt rules

- The first prompt never states a total and never asks for math.
- `raw_text` is the line exactly as printed.
- Boxes are requested only from models that Phase 0 shows can give them (VD7).
- **The prompt that ships is the prompt that was scored (N3-9).** Phase 0 scores box-capable models with the box prompt and the others without it. `prompt_version` in `reading.csv` records which.

### Text sources

- **Alias lookup:** the vision `raw_text`, normalized as today.
- **Location and vendor matching:** the vision `ReceiptHeader` fields, as with today's model-extracted header.
- **Printed total:** the vision header's total.
  - **N2-10:** the vision reader turns off today's `total_from_text` override (`stages.py:156-165`), because Tesseract is the source of #121's misread totals. The override stays on for the text path and arm (b).
  - The OCR regex `printed_total_line` is a witness. It raises `total_witness_mismatch` when it finds a different total.
  - When OCR finds no total line, or there is no OCR text, there is no mismatch flag; that case is covered by `no_witness` (R2-18).

### Consensus (VX4; VD2–VD5)

- **Second reader (VD2).**
  - `VISION_SECOND_MODEL`, from a different family than `VISION_MODEL`, picked by Phase 0. It reads lines only.
  - **Order (N2-12):** primary reading, then post-passes, then the witness pass, then the second-reader decision.
  - **Does it fit (EV3)?** Before starting it, the reader estimates the second reading's time: the primary's `completion_tokens` ÷ the primary's measured tok/s for this call, plus about 4 s of swap. If that exceeds the stage time left, it is skipped with `second_reader_skipped`, and the primary stands. Consensus therefore covers short and medium receipts, up to about 60 lines; this is stated, not hidden. D12 (the per-stage cap) stays.
  - It runs when any of these holds:
    - the primary reading doesn't reconcile;
    - any line is `ocr_unsupported`;
    - the purchase has `total_witness_mismatch` (D13).
  - Under `no_witness`, lines aren't flagged `ocr_unsupported`, so the second reader runs only on non-reconcile. Agreeing, witnessed receipts cost one call.
- **Alignment (VD3, R2-15).**
  - Each reading runs through the post-passes.
  - A deterministic sequence alignment then pairs item lines, using position and normalized `raw_text` similarity, with the amount as a tie-break.
  - Paired lines agree when their Decimal amounts are equal.
  - A line only one reader saw is an "extra line" candidate.
- **Candidates.** Each disagreeing line has up to 3 candidate amounts:
  - the primary reading's;
  - the second reading's;
  - an OCR token amount, when the line's two readings differ and exactly one OCR token falls between them in digit pattern.
- **Independence (C2-4).** A candidate counts as supported only by a source other than the one that proposed it. OCR can't support its own candidate.
- **Search (VD4).**
  - Agreed lines are fixed.
  - Up to 12 disagreeing lines × 3 candidates are tried, which is at most 531,441 sums in Decimal, under a second.
  - **Extra lines (D17, N3-3).** A line only one reader saw enters the search with two candidates: its amount, or excluded (zero). It counts against the same cap. If a unique reconciling combination includes it, the line is ticked and labelled "added: matched the total". Excluding a line never deletes it; it stays an unticked row.
  - Over the cap, the search is skipped with `consensus_too_wide`.
  - **Exactly one combination within 0.02 of the vision header's total:** it is preselected, and its lines carry `matched_total`.
    - A chosen candidate that no other source supports is still allowed. Its button reads "only the total supports this".
  - **Disputed total (D13).** With `total_witness_mismatch`, nothing is preselected. Review shows both totals (D18).
  - **Non-item disagreement (OV8).** If the readers disagree on any discount, tax, deposit or fee line, nothing is preselected (`consensus_open`), and review shows both readings for that line.
  - **None, or more than one:** nothing is preselected, and the purchase gets `consensus_open`.
- **Pruning (Section 7).** The search stops a branch when the remaining candidates can't bring the running sum within 0.02 of the total, so the worst case stays well under a second.
- **Purity.** `ingest/consensus.py` has no I/O and is property-tested with Hypothesis: a preselected answer always sums within 0.02, two fitting combinations never preselect, and the cap is never exceeded.
- **Storage.** The lines stage output keeps every reading and every candidate. The draft lines take the preselected or primary amounts.

### Witness pass

`witness_amounts(lines, ocr_text)` is deterministic.

- **OCR source.** When `READ_ADAPTERS` starts with `vision`, the OCR stage still runs: client text when present, otherwise Tesseract. If no adapter produces text, the stage records empty text instead of failing, and the purchase gets one `no_witness` flag.
- **Matching (R2-16).**
  - Text is split into numeric tokens at non-digit boundaries other than `.` and `,`.
  - An amount is supported by an exact Decimal match. It is also supported by its digits with the separator removed, when that digit run is 3 or more long, but only if Phase 0's false-support rate for digit runs is under 5% (OV11). Above 5%, the `WITNESS_DIGIT_RUNS` setting is off and only exact matches count.
  - Tokens are assigned in line order: every line's exact matches first, then digit-run matches. Each token supports at most one line.
- **Flags.**
  - Per line, `ocr_unsupported`.
  - Per purchase, `witness_weak` when more than 25% of priced lines are unsupported.
  - Flags never block anything.
- **Headline metric (R2-1).** In production reporting, a receipt still counts as reconciled when it carries `witness_weak`, and both flags are reported beside the share. A receipt with `total_witness_mismatch` counts as not reconciled until a person confirms the total (D13). Phase 0 always scores against the committed total.

- **Every unsupported or disagreeing amount is visible in review.**
  - Each such line shows `ocr_unsupported` or its candidates.
  - No purchase skips the review step (unchanged).
- **No model, no change.** With no model reachable, ingest waits and retries exactly as it does today. With the vision model missing, it falls back to text at once.
